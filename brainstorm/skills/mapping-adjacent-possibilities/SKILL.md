# Mapping Adjacent Possibilities

Map changes in **reachability**, not an inspiring list of things that might eventually happen. An unlocked option is not yet an outcome, an obligation, or proof of demand.

## Establish the before and after

Name the immediate task, present capabilities, binding constraint, and resources actually available. What does completing the task change? Be specific: a reusable interface, a verified capability, a relationship, permission, knowledge, time, or cash.

For each proposed adjacency, connect:

**New capability → remaining prerequisites → reachable option → cost and condition for exercising it.**

If the task does not materially change that chain, the opportunity is merely related, not unlocked by it. If several prerequisites are jointly necessary, show the conjunction; removing one does not remove the others. Distinguish capabilities that already exist from those merely proposed.

## Separate three kinds of edge

- **Enabled now:** the material prerequisites are established and the next step is feasible within current constraints.
- **Conditional:** this action removes a relevant constraint, but named requirements, demand, permission, or resources remain unresolved.
- **Speculative:** the causal connection itself lacks support. Keep it as a hypothesis only if it changes a useful investigation.

Availability of data is not authority to reuse it. Technical feasibility is not customer demand. A new skill is not a customer pipeline. Do not manufacture numerical probabilities or financial option values to make these jumps look measured.

## Account for the cost of optionality

For a promising option, ask what it costs to keep open, what must be spent to exercise it, what would make it expire, and what other option it excludes. Preserve optionality only where those costs are justified; an unused platform can consume the runway it was meant to protect.

Do not count the same shared capability repeatedly as independent upside. Do not add mutually exclusive futures as though all will be realized. An option may depend on the success of an earlier uncertain choice, so a long chain can be less useful than a small immediate gain.

A focused solution can create cash, actual users, reusable knowledge, and a credible next experiment. A platform earns its status through supported reuse and demand—not its architectural generality. Learning breadth is not always better than a specific skill that removes the current constraint.

## Choose the next frontier

Compare the immediate outcome with the credible options it creates, the resources it consumes, and the alternatives it closes. Include staying with the current approach or a smaller enabling step.

Sequence only the prerequisites needed for the chosen next outcome. Do not build every enabling layer in advance. Map far enough to distinguish the current choices; stop extending a branch when unsupported prerequisites dominate or another level would not change what comes next.

Recommend the next action and the observation that would justify exercising a later option. Keep unchosen opportunities available in the existing work record if useful; do not silently add them to the authorized task or start parallel projects.

## Deliver

Show the immediate capability, the material reachable or conditional adjacencies, their shared prerequisites and costs, and the next supported move. Make the speculative boundary visible. A small opportunity map with a justified decision is more useful than a large optimistic tree.

**An option is valuable when you can afford to recognize, preserve, and exercise it—not merely imagine it.**
