# Exploring Possibilities

Expand the space of **different causal moves**, not merely the number of suggestions. Keep the user's outcome fixed while allowing the route to change.

## Set the exploration boundary

Extract the intended outcome, relevant evidence, binding constraints, and assumptions open to challenge. Use supplied context before asking for more. The absence of a detailed brief is not a reason to begin a long interview: state provisional assumptions when they are harmless and relevant.

A genuine preference or permission boundary is not an obstacle to creativity that may be discarded. A hypothetical reversal can expose a constraint's role, but it is not a recommendation to violate it.

## Generate by changing a dimension

Name the conventional approach so its variants are visible. Then vary a relevant dimension:

- **Representation:** one identity with different views instead of replicated objects.
- **Sequence:** defer a decision until its answer matters, or surface a prerequisite earlier.
- **Boundary:** remove a handoff rather than improve its messaging.
- **Participation:** change who supplies, verifies, or consumes an input.
- **Constraint:** remove an assumed limitation while preserving the actual contract.
- **Composition:** combine existing capabilities so their interaction supplies a missing function.

These are generators, not mandatory categories or prescribed solutions. Explain each candidate as **change → mechanism → new possibility → dependency or failure boundary**. Collapse candidates whose causal move is the same.

Allow a speculative branch to develop before evaluating it against the incumbent's implementation details. Do not turn brainstorming into immediate rejection. But do not promote an imagined capability, market, scientific fact, or legal permission into an established premise.

## Reach sideways with a reason

Restate the constraint in domain-neutral terms. Seek another field in which that constraint matters, then map an actual operation back to this task. Verify factual claims about the source when using them as evidence; otherwise label the transfer speculative.

Different vocabulary or a remote industry is not proof of a different idea. Find the invariant that transfers and the condition where it breaks. A random association may start a branch, but cannot justify retaining it. A technology name is not a mechanism: identify the inputs, state change, and observable result. Inference about activity is not verification of progress; encryption is not access authorization. If the needed property is unverified, expose it as a dependency rather than hiding it behind a sophisticated label.

## Harvest without premature consensus

After generation, compare the real differences: which candidate removes the most consequential friction, which depends on an unverified premise, and which offers a cheap informative trial? Keep uncertainty and incompatible possibilities visible when evidence does not settle them.

Recommend a promising direction or discriminating experiment when useful, without making the user rank a raw idea pile. If the request is exploration only, leave the alternatives open rather than forcing a commitment. Do not build or launch anything merely because it was imagined.

Respect an explicit requested number of ideas. Otherwise stop when additional candidates repeat existing mechanisms or no longer bear on the outcome. Do not fill a quota with cosmetic variants or claim novelty because the result surprised you.

## Deliver

Give the distinct directions, why each could work here, their important assumptions, and the cheapest way to learn which deserves more attention. Use concrete examples of the user's workflow rather than a tour of evocative domain names. Do not print the entire generating process or repeatedly ask "which thread should I pull?"

Read [FRAMEWORKS.md](references/FRAMEWORKS.md) only for a chosen generative move. [RESEARCH.md](references/RESEARCH.md) is a legacy reading list, not verified support for this particular prompt; inspect primary sources before repeating empirical claims. If the user switches to a specific authorized task, stop diverging and do that work.

**Make the alternatives genuinely different before making any of them elaborate.**
