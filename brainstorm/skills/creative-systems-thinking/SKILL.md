# Creative Systems Thinking

Design the version whose mechanism changes what becomes possible. "Build it for yourself" means make the experience concrete; it does not mean substitute the model's preferences for the user's or discard other users' needs.

## Hold the experience still; change the mechanism

Select a representative journey from the available context: a person has an intention, encounters some state, acts, and learns the result. Name the friction and the constraints that must survive. Use a real artifact or scenario rather than an abstract list of desirable qualities.

Identify the conventional answer and what it gets right. Then vary a load-bearing choice:

- **Representation:** Is the same thing copied into containers when one identity with multiple views would suffice?
- **Boundary:** Is coordination necessary because work was divided at the wrong place?
- **Interaction:** Does the user have to reconstruct state that the system could expose directly?
- **Timing:** Is a decision demanded before its answer matters, or information delivered after its useful moment?
- **Ownership:** Could an existing source of truth eliminate a reconciliation step without losing accountability?

Do not use every lens by rote. Follow the one that changes this workflow; use another to challenge it.

## Use the phoropter

Keep the same task and evidence while switching between designs: better here, worse where? Changing the use case between demonstrations makes an attractive alternative impossible to compare fairly.

For each serious candidate, walk the concrete journey and a failure or correction path. Identify what the developer must maintain, what the user must understand, and what an agent would need to observe and verify. A lens that changes presentation but leaves the friction intact is not a new mechanism.

Non-hierarchical organization, contextual views, linked identity, and reuse without copying are candidate properties—not an automatic prescription for a graph, a new database, or a particular thinker's entire system. When borrowing an idea, explain the operation it enables and the invariant it must preserve.

## Borrow an operation from elsewhere

Restate the constraint without project nouns. Find a domain that handles that constraint, inspect a concrete example or reliable source, and extract the operation—not its fashionable vocabulary.

Map what is shared and what differs. Ask which differing condition would invalidate the transfer. If no source can be checked, label the borrowing a hypothesis; do not invent an attribution or pretend the analogy is evidence of effectiveness here.

Bring the transferred operation back to the same representative journey. If it cannot explain a different action, state transition, or recovery path, it is decoration.

## Prototype the disputed move

Choose the cheapest safe representation that could distinguish the designs: a worked data example, a small interaction sketch, a trace, or an authorized prototype. State what observation would favor one over the other. Do not build the entire platform to evaluate one interaction.

Count the friction moved elsewhere: new synchronization, permissions, migration, cognitive load, or maintenance. Prefer a step-change in usefulness over a larger collection of individually attractive features. Creative freedom does not expand authorization, remove safety boundaries, or change the task's goals.

Return the strongest supported design, the mechanism behind it, a concrete before/after journey, and the tradeoff or next experiment. If the evidence favors the conventional design, retain it and say why. Do not force a novelty claim or leave a menu of interchangeable ideas for the user to resolve.

**Change what the system makes easy—not just how imaginative its description sounds.**
