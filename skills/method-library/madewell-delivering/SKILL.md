# Delivery

One selected task receives its own approach, fixed brief, actual result and independently supported verification. A collection of candidates does not become one enormous delivery, and selecting Delivery does not authorize execution.

This is an unpublished method proposal, not an accepted shipped default. This guide selects responsibilities rather than duplicating their method bodies or operating a workforce.

## Select the needed responsibility

The opinionated default is **Ideation → Planning → Implementation → Verification**:

- **Ideation:** establish success for this task and choose a grounded approach, reusing settled context rather than restarting open-ended Brainstorm.
- **Planning:** settle an actionable fixed brief and feasible evidence ownership/availability before making.
- **Implementation:** perform that accepted brief within actual authority, retaining real artifacts, partials and failures.
- **Verification:** independently compare the actual result with every current condition and report attributable observations, failures and unknowns.

These are descriptive selections of separately available methods, not sibling-file read instructions. Use the host's supported loading path for selected bodies; a name in a catalog does not mean instructions were applied. If an explicit method is unavailable, report the gap instead of silently falling back. Components can be selected alone, repeated, extended or replaced compatibly while preserving their enclosing contract. Do not fabricate predecessor work, require a fixed fleet/call count, or create four candidate tasks just to mirror the default. An independently owed prerequisite artifact may be its own task with its own delivery.

## Carry the task intact

Receive the exact selected task, intended outcome/source, requirements/dispositions, boundaries, artifacts/conditions, real dependencies, settled decisions, scoped answers and unresolved questions. Preserve identities and actual source versus interpretation. Rough task material can need substantial ideation; it must not be silently replaced by an easier research outcome. A missing prerequisite remains owned and visible.

Ground spans shaping/planning against actual material. Rumen carries applicable mechanical fences, independent judgment, operator guidance and vocabulary through making/checking, with evidence owners intact. Neither is an extra serial stage. Provision every configured successor with the actual contribution and resolvable permitted inputs; keep private maker tracks private and reprepare stale material without deleting history.

For software's independent split, implementation and independent acceptance-check design work from the same fixed plan without seeing each other's private making. The authorized non-maker executor receives the candidate and checks. A different label alone is not independence. Do not require code, Git, repositories, deployment or test commands for non-software work.

Each current condition needs an evidence owner, accessible inputs and availability boundary. A candidate checker cannot rely on its own future report, future release or inaccessible private material. Live observation, manual judgment and engine provenance need their own actual producers. The maker neither runs its independent acceptance checks nor awards itself acceptance. Valid shape, source publication, process success and historical completion do not prove the intended outcome or live usability.

Use NQ for each agent exchange: confirm understanding, reuse scoped answers, ask concrete unclear/ambiguous/missing inputs only, and preserve identities and answered-turn count. After three answered turns with unresolved questions hold the affected work for a specification defect and alert its responsible human. A clear brief needs no ritual questions. Save transitions/partials before successors proceed in the existing work record when supported; disclose absent persistence. Recover saved results/receipts after interruption; uncertain effects are not permission to repeat them.

## Effort and return

Light is the free default: select the useful current responsibility and preserve all required scope, conditions, evidence ownership and handoff material. Focused additionally reconciles a critical interface or evidence-availability seam between selected responsibilities. Deep additionally traces a difficult dependency/failure/recovery path through actual available material and prepares its affected continuation. These guide-level additions do not silently upgrade every child method. Implementation gains additional work only when already included in its fixed brief; absent such work there is no distinct Deep implementation variant.

Report requested, authorized/effective and performed effort with actual seam/dependency findings. Standalone public use is unrestricted by managed commerce. Managed paid Focused/Deep operations need service authorization; missing access/capability requires disclosure and an explicit alternative, not silent substitution. No effort reduces required correctness, safety, privacy, evidence or recovery, chooses a provider, or expands action authority.

Return natural Markdown: task/outcome, current contribution and actual artifacts, condition/evidence status, unresolved owners and next selected handoff, actual effort and limits. Stop at the selected responsibility's real boundary or a precise blocker. Source-ready, reported complete, independently verified and live usable remain separate claims. When Landing is selected, hand off the actual unit's artifacts, verification evidence and unfinished propagation; its separate method returns Delta, Learned, Propagated and Tax without substituting automatic release or cleanup.

**Example:** A task to produce an approved sales-call script can finish with the actual script and independent evidence against its conditions. Delivery does not imply contacting prospects, and a separate live-call outcome cannot borrow the script's acceptance.
