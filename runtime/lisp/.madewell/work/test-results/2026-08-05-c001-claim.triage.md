## Root cause

- **File:** `.madewell/work/verification/claim-verify.lisp` (and its byte-identical
  embed in `.madewell/specs/2026-08-05-c001-claim.test.md`), test
  `i4-worker-never-learns-recovery-choice`.
- **Form:** the `flet`-bound worker —

  ```lisp
  (flet ((worker (subject value trail)
           (push :before-door trail)
           (let ((door (constellation:ground subject value)))
             (push :after-door trail)
             ...)))
    ... (worker "w" 7 trail-a) ...)
  ```

  asserted later as `(equal (nreverse trail-a) '(:before-door :after-door))`
  (and identically for `trail-m`, `trail-r`).
- **Mechanism:** `trail` is a *function parameter*. `(push :before-door trail)`
  macro-expands to `(setq trail (cons :before-door trail))` — a rebinding of the
  callee's local variable. Common Lisp passes the caller's variable's *object*
  (here `NIL`), not the variable itself; nothing `worker` does can reach
  `trail-a`, `trail-m`, or `trail-r`. All three remain `NIL`, `(nreverse nil)` is
  `NIL`, and `(equal nil '(:before-door :after-door))` fails — deterministically,
  three times, with **zero dependence on `ground`'s behavior**.

**Reading of the FiveAM report (both arg-order readings converge):** the failure
line shows `'(:BEFORE-DOOR :AFTER-DOOR)` evaluating to `(:BEFORE-DOOR
:AFTER-DOOR)` — the quoted literal's only possible value — "not EQUAL to NIL".
NIL is therefore the value of the `(nreverse trail-*)` side. The runner's
`fff......` line matches code order exactly: the trail checks are `is` forms 1–3
of the nine in I4; forms 4–9 passed.

**Contrast with the green sibling:** I3 (`i3-restart-acquire-resumes-in-place`,
passed) records its trail from a lambda that *closes over* `trail` directly —
`(push ... trail)` there mutates the shared lexical cell. The designer used the
closure idiom in I3 (correct) and the flet-parameter idiom in I4 (broken). Same
intent, broken plumbing.

**Evidentiary content of the failures: none.** The trail variables are
unreachable from inside `worker`; they would be NIL for any implementation of
`ground`, correct or broken. Meanwhile I4's six passing checks establish the
intent-level property directly: the restart menu was identical at the door
(`subsetp` over `seen-a`), the worker call shape was identical across runs
(subject equality checks), and the worker received exactly the door's return
value in all three recovery modes — a grounded claim under `acquire`
(`groundedp` of `res-a`'s door), the honestly marked claim under `mark-unknown`
(`claim-value` `:unknown`), and `NIL` under `refuse`. Those return values are
constructed *after* `ground` returns inside the worker body, so the worker
demonstrably crossed the door and kept computing in every mode — precisely what
the trails were meant to instrument.

## Does intent 4 hold in the implementation as written?

**Yes.** "The worker never learns which restart was taken or by whom" holds in
`src/claim.lisp` as written:

- The door (`ground`) establishes all three restarts itself via `restart-case`;
  the worker at the door names nothing and chooses nothing. The choice arrives
  from outside — a handler up the stack (in the suite: `observe-ungrounded`'s
  handler; in the design: a coordinator or `with-grounding-policy`) — via
  `invoke-restart`, and the restart's value becomes the door's return value, in
  place, with nothing re-run (the `acquire` restart tail-calls `ground` with the
  supplied acquisition; `mark-unknown`/`refuse` return their values through the
  same `restart-case`).
- What crosses the door into the worker's code is only the return value. The
  condition object, the restart objects, and the identity of the chooser never
  enter the worker's interface. `with-grounding-policy`'s own docstring states
  the invariant: "Workers inside BODY never learn which was chosen."
- One honest nuance, reported not asserted: the door's return value necessarily
  *differs* by decision (grounded claim / `:unknown`-marked claim / NIL), so the
  worker can infer the decision's effect from what it received. That is the
  design's honest-outcome semantics — `mark-unknown` is defined as handing back
  an auditable absence record — not a leak of the choice or the chooser. Neither
  the restart taken nor who took it is communicated as such. The package brief's
  own phrasing — "Recovery is named by the worker, chosen elsewhere" — is exactly
  what the code does.

## Cross-impact clause — what changes or breaks under the obvious fix

The obvious fix is test-side: give the worker body real lexical access to the
trail — either (i) three lambdas each closing over their own `trail-*` variable
(the I3 idiom), or (ii) one shared worker function passed a mutable cell
(`(push :before-door (car box))`) or returning the trail in its result list.
Consequences:

1. **Touched files: exactly two, both test-side.** The executable
   `.madewell/work/verification/claim-verify.lisp` (the I4 test form only) and
   the byte-identical embed inside the test brief — the project's own convention,
   exercised in this cycle's spine repair, requires the embed be updated in
   lockstep. **Zero** changes under `src/`, `tests/`, `constellation.asd`,
   `src/package.lisp`. The system under test is untouched; no behavior of the
   implementation changes.
2. **Expected post-fix run: 72/72, exit 0.** I4's six other checks already pass
   against the current implementation; the three repaired trail checks pass
   trivially once the trail is actually recorded, because the worker demonstrably
   crosses the door in all three modes. The existing results file's headline
   "FAIL — 3 of 72" becomes historical; a re-run through the Test-Runner role
   must supersede it (same disposition as the spine package this cycle).
3. **A weakening risk to police in fix variant (i):** the test's stated property
   is "ONE worker thunk runs under all three restarts." Three same-bodied lambdas
   preserve the intent ("the worker body never changes") but no longer share one
   function object. If literal sameness matters, variant (ii) keeps a single
   `flet` worker. Either way, the check count (9 in I4, 72 total) and the other
   six check forms should stay byte-stable; only the trail plumbing moves.
4. **No downstream coupling breaks.** Nothing else reads `trail-a/m/r`; there is
   no run-order dependence (spine hygiene lives in `with-clean-spine`, temp files
   in `with-temp-file`, both orthogonal); the acquisition counter advances
   identically. Repairing I4 perturbs no other check's inputs.
5. **What does NOT change:** the green verdicts on intents 1–3, 5, 6 stay green;
   the designer's reported ambiguities A–G (operator-asks, refuse-returns-NIL,
   `:unknown` marker, policy designator inertness, unhandled-is-error, `groundedp`
   domain, door telemetry) are unrelated to this plumbing and remain open for the
   coordinator; this suite's exit-code aggregation (`(uiop:quit (if (fiveam:run!
   ...) 0 1))`) is correct — unlike the sibling spine suite's — so no main/gate
   repair is needed here.
