## Root cause

**File:** `.madewell/work/verification/spine-verify.lisp`
**Form:** `MAIN`'s verdict aggregation (lines 340-348) —

```lisp
(let* ((results (fiveam:run! 'spine-verify))
       (failed (count-if (lambda (r) ...) results)))
  ...)
```

**Mechanism:** `fiveam:run!` does not return a result list. Verified at the
pinned vendored source this session (`run.lisp:286-296`): `run!` is
`(explain! (run spec))`, and `explain!` "Return[s] a boolean indicating
whether no tests failed" via `(results-status result-list)`
(`run.lisp:147-158`: T when no `test-failure-p` results, NIL otherwise). The
designer assumed `run!` returns what `fiveam:run` returns (the result list).

On this all-pass run: `results` = `T`; `count-if` requires a `SEQUENCE`; `T`
is not one → unhandled `TYPE-ERROR` under `--disable-debugger` → SBCL exits 1
*before* the verdict line, before the final `(cst:spine-reset)`, and before
`(uiop:quit code)`. Exactly what the runner's backtrace frame 0 shows:
`(COUNT-IF #<FUNCTION ...> T)`.

**Latent second branch, same form:** on a *failing* run `run!` returns `NIL` —
which IS a sequence (the empty list). `count-if` over `NIL` yields 0, `length`
yields 0, and the verdict line would falsely print `0 check results,
0 failures` while exiting 1 only by accident of `(and NIL ...)`. The
aggregation is wrong on both branches; only the all-pass branch crashes. As
shipped, this suite reports RED when green and lies in the tally when red.

**Why the process didn't catch it earlier (and why that is not a process
failure):** the designer compile-checked (`warn=NIL fail=NIL`), but a boolean
flowing into `count-if` is a runtime type error — `compile-file` cannot see
it. Designer/Runner separation forbids the designer from executing, so the
first real run belonged to the runner, who reported it verbatim without
repairing it. The separation worked as designed; the artifact was defective.
Context from the board: the same fact (`run!` → boolean) was independently
discovered by td-escalate (finding 07:09:59Z) and acted on pre-run by
td-supervisor (finding 07:16:29Z, who rewrote their main to `fiveam:run` +
`fiveam:explain!`). td-spine's suite simply shipped before that knowledge
propagated.

## Cross-impact clause — what changes if fixed the obvious way

The obvious fix (the td-supervisor pattern, staying on exported FiveAM API —
`run`, `explain!`, `results-status` are all exported in the pinned version;
`test-failure-p` is not): `main` calls `(fiveam:run 'spine-verify)` for the
result list, derives pass/fail from `results-status` (or `explain!`'s boolean)
instead of the class-name string-search heuristic, prints the verdict line
with the real counts, then returns the exit code.

1. **Blast radius is exactly two files, both test-side.** The executable
   `.madewell/work/verification/spine-verify.lisp`, and the test brief
   `.madewell/specs/2026-08-05-c001-spine.test.md` — the brief embeds the
   suite byte-identically and declares it canonical ("identical content"), so
   both must change in the same breath or the brief lies. Zero changes to
   `src/`, `tests/`, `constellation.asd`, or any other c001 suite. The
   implementation and its 53 checks are untouched.
2. **The run's outcome flips with zero change in underlying behavior.** An
   all-pass run goes from exit 1 (crash) to exit 0 with the verdict line
   printed — the brief's exit-code contract becomes true for the first time.
   Any gate keyed on the exit code (orchestrator tally, future CI) flips RED
   → GREEN. The existing results file's "exit 1" headline becomes historical
   and must be superseded by a re-run through the Test-Runner role (separation
   of roles still holds: triage does not repair, the designer repairs, the
   runner re-runs).
3. **The red-path lie dies too.** Post-fix, a failing suite prints real
   failure counts and exits 1 *because* failures exist, not because `(and NIL
   ...)` collapses. Anyone diffing future suite output should expect the
   verdict line's numbers to become meaningful for the first time.
4. **One edge semantic to keep explicit in the rewrite:** with `fiveam:run`,
   an empty result list (a suite that runs zero checks) makes `(and results
   (zerop failed))` false → exit 1. A suite that checks nothing is RED. That
   is the safe reading; the fixed `main` should preserve it deliberately, not
   inherit it silently.
5. **A fragile heuristic becomes deletable.** The `search "FAILURE"/"ERROR"`
   class-name matcher was only needed because the result list was assumed
   available; once `run` actually provides it, exported `results-status` (or
   `explain!`'s boolean) replaces the string match. No new pin on FiveAM
   internals is introduced.
6. **First-time-reachable tail code changes what the process leaves behind.**
   The final `(cst:spine-reset)` before `uiop:quit` has never executed (the
   crash precedes it). Post-fix it runs, honoring the suite's own
   state-discipline promise end-to-end — cosmetic in a one-shot process, but
   it means the suite finally exits through its intended path. Expectation
   for the re-run: the identical 53/53 tally, the verdict line, exit 0.
   Anything else is a new finding, not part of this triage.
